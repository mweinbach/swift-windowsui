# Retained Button action ownership — source candidate

This prerequisite supports the existing goal.md control and data-browser requirements. It does not add a new product requirement or change Table sorting semantics. The source includes the approved [native transfer receipts](RetainedButtonActionTransferProposal.md); independent source review, composition, and serialized validation remain required. No new or existing XCTest case has been compiled or run for this packet.

The guarded payload is the action authored for Controls.button, plus the ordinary WinSwiftUI Button invalidation that follows that action. The retained node owns this payload through an optional owner. Primary and repeat dispatch closures hold that owner weakly. Generic non-Button event handlers are unchanged.

A non-nil onActivate wrapper may continue to delegate to the old Button handler. Its own effects before or after delegation are outside the Button owner and are not promised revocable. Setting onActivate to nil, replacing the Button declaration, physical departure, or terminal close retires the original payload permanently. Assigning the saved closure back cannot revive it. Removing repeat activation retires only the repeat route. Focusability, hit testing, and accessibility response modifiers remain independent route policies; they are not substituted for the common lifetime check.

Each physical node retains one native in-flight gate across declaration replacement, including Button → passive view → Button. An invoked payload is pinned in a separate helper until its action, guarded completion, and destructor have unwound. A newly adopted declaration on that same node cannot reenter while the older invocation holds the gate. An action that removes or replaces its declaration cannot continue through the old ordinary Button invalidation. Alert actions retain their existing presentation receipt and completion behavior.

Construction and acceptance are separate:

- An idle, never-attached Controls.button or ordinary Button remains usable directly. Its runtime argument and setRuntime alone are not candidate acceptance.
- Root builds, managed or unmanaged GeometryReader builds, and lazy preparation enroll new Button owners in a balanced frame for that exact runtime. Nested frames retain their predecessor and restore it only when they still occupy the runtime slot.
- A yielded lazy Candidate retains its original pending cohort. While pending, its permission also checks that exact Candidate's native currentness through a weak reference; keeping an obsolete Candidate alive does not authorize a later unrelated adoption. Explicit discard and the Candidate's own isolated deinitialization retire every still-pending member before releasing any owned fields, even when a nested Candidate still retains the original construction frame. Direct construction frames also have isolated cleanup. Externally retained source nodes do not keep abandoned action authority alive. Accepted owners clear this permission and remain independent of Candidate release.
- Adoption acquires an exact, separate claim on a source owner. A nested adopter cannot borrow a pending source already claimed elsewhere. Older cleanup does not retire a declaration accepted by a newer operation.
- Adoption holds runtime construction frames through matching and property-payload cleanup. Rejected-payload destruction and Candidate field release run with a closed cleanup frame, including when a Candidate previously left its construction frame. Restoring a frame skips predecessors that already left. Destructor-created controls cannot escape as idle standalone actions.
- Accepted transfer clears the source node's owner field without retiring the destination owner. Candidate cleanup only consumes owners that still belong to the original pending permission.
- Observing source roots never enrolls or retires an already accepted owner or a different frame's pending owner. Merely parenting an idle Button under a detached construction wrapper is not accepted publication; that Button can still enter a later Candidate.

The source owner is a payload-bearing retained-source field. ComponentHost records its preparation and accepted property copy through the existing lazy/descriptor journal. Native Button witnesses supplement ordinary reconciliation; they do not replace provider, lease, journal, subtree completion, or UIA authority. Matching suspends affected physical gates before authored key hashing or equality. Identity assignment has its own native stamp, including equal-value reassignment; a deliberate property copy refreshes that stamp immediately beside the pinned native write.

Finalization occurs after node properties and children have completed. It releases rejected payloads while affected actions remain suspended, then checks the original concrete NodeReconcileAdmission and complete subtree snapshot again. The accepted Boolean from before destruction is not sufficient. All proposed owners receive a native acceptance preflight before the no-callout acceptance writes.

The completed subtree snapshot also captures each node's original optional Button owner weakly, including absence and its retired state. Managed insertion delivery can call the runtime clock after the Button adoption batch has closed. A clock that clears, replaces, or retires that owner invalidates the original completion before insertion animation states are published. Restoring the same retired owner cannot revive the old snapshot. The exact-witness compaction comparison includes the same metadata; it cannot merge snapshots with different owner presence, identity, or retirement state. This adds one weak reference and two Boolean fields per existing node snapshot, no new traversal or strong action-payload retention. It does not add an owner-slot generation token for a node that began and ended without an owner. The storage stride and runtime cost have not been measured for this source packet.

This is an extension of the existing completion evidence used by Activity publication and cleanup, not a reopened Button adoption batch or a new Activity permission. Already accepted insertion events and journal entries remain historical facts when later work is refused; their claimed cleanup still finishes. The original effective insertion transaction is staged before owner-copy payload destruction. Candidate discard marks both the insertion plan and Button permission unavailable before dropping insertion recipes, and its closed construction frame spans those payload releases. The Activity implementation and insertion-plan source are unchanged by this composition. Existing root, reader, row, and prepared-subtree consumers keep their snapshot boundaries; the prepaint observation also uses this type, so an owner change during its callback window now rejects that original paint observation.

Native retirement prepasses do not destroy Button payloads. They pin the original owner cohort and mark it first. Ordinary removal releases that cohort after its existing task and callback cleanup. Terminal stop stores the cohort on the runtime; only the outermost existing cancelRenderLifecycleTasks completion releases it, after editor, State, and task authority has been revoked. That completed phase drains cohorts added by payload destructors that call stop without asking for another cancellation. Overlapping retirement scopes defer a shared owner's release until their last cleanup boundary. Native teardown visits the complete tree with a visited set; the renderer's diagnostic depth limit must not truncate editor, dialog, List, or Button revocation. The owner retains the runtime's native logical-host lifetime token, so dropping a closed runtime cannot reopen a never-attached action.

An already retired retained payload remains dead, but does not permanently disable its physical node. A fresh accepted declaration can replace it. Witnesses capture the original owner retirement state, reject later changes, and refresh the owner slot only beside its deliberate native copy. Explicit nil activation retires and clears the owner slot while pinning its old owner and handler across the writes; the physical flight remains on the node. A fresh source with its action explicitly cleared can therefore contribute its visual declaration without carrying a dead action owner. A source still carrying a retired owner is ineligible. New declarations after nil activation or physical ABA must work without reviving any saved old handler.

Its review identified early payload release, missing dropped-Candidate cleanup, weak-runtime revival, missing ordinary identity stamps, cached final admission, cleanup-tail construction escape, cross-adoption source borrowing, and insertion ABA. Review of the 1cfc613 successor then found a nested Candidate retaining an abandoned frame, stop-only reentry pinning later payloads, and the teardown depth regression. The authored repairs and preservation cases remain subject to immutable source review and later execution. The source now includes the separately approved insertion and parent-table receipts.

Scheduled departures retain their native witnesses until actual departure is claimed. Temporary-source and retained-root ancestors are witnessed before any matching callback. During insertion, only an adjacent deliberate native attachment or child-table write advances that specific expectation; controller and dismantling callbacks never authorize a later refresh. Public removal passes no adoption receipt, so a callback cannot disguise its own detach/reattach as the framework's planned transfer. Already-claimed retirement and task cleanup still drains after refusal.

Ancestor witnesses retain only weak owner metadata and never take part in payload cleanup. An already mounted passive source still uses its supported reparenting path. Its original physical departure cohort is captured before removal, and cleanup follows each node's original attachment and in-cohort parent path independently of Button insertion permission. Destination rejection or close therefore does not skip old disappearance, task, or controller cleanup. Actual reattachment stops later old attachment writes; captured old controllers cannot detach their newer attachment. Only deliberate native writes advance the local departure receipt, and global Button refusal cannot be reopened by that cleanup.

The source cohort also captures each runtime's original pointer sequence, separate hover and indicator slot identities, and original interaction target attachments before any departure callback. A later exit, drag, dismantle, or controller callback cannot make its new hover part of the old cleanup. Inner helpers check those original slots and physical targets around callbacks and clocks. A superseded hover does not skip other cleanup still owed by the original pointer. Disappearance keeps original keyed task handles reachable by its hooks, so explicit cancellation still runs synchronously inside the hook; exact old handles are removed at the existing terminal cancellation phase.

The original four source test files contain 94 methods covering owner lifetime, construction, teardown, and final native admission. Their exact blobs and the six separately approved RetainedButtonRemovalResolverCompositionTests methods remain unchanged in this projection. The original three insertion tests retain their strict refusal assertions; positive insertion and additional ancestor, scheduling, disabled-declaration, mounted-source cleanup, controller replacement, task cancellation, and callback relocation regressions accompany them. Those cases require the original explicit task-cancellation order and preserve a callback-installed sibling hover through a successful transfer, including its later public exit. The separately reviewed RetainedButtonActionTeardownTests packet adds real retained-host State/editor/task release probes without creating a native window. New RetainedButtonInsertionCompositionTests exercise the completed owner witness at insertion clocks and its exact equivalence and weak lifetime. Unchanged regression suites remain part of the future execution plan. Contract checks and swift-format are source checks only; they are not evidence of compilation, XCTest results, native UI behavior, or Table completion.

The ordinary raw transition-overlay owner remains an inherited limitation, investigated separately: reattachment from controller willDetach can leave the old executable overlay scheduled for later disappearance. This packet preserves its existing animation/disappearance timing and does not claim complete overlay safety.
